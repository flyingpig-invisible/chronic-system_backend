## 二、当前状态（本次会话完成的内容）

### A. 患者数据权限：从「查库算集合」改为「SQL 子查询」（关键重构）

**改造前的问题**

原实现在 `DataPermissionInterceptor` 的 `getSqlSegment` 中调用 `PatientDataScopeService` 查库取「可见患者 ID 集合」，再把集合拼成 `patient_id IN (...)`。而这套查库本身又会被同一个拦截器改写，只能靠以下补丁维持：

- `ThreadLocal<ScopeCache>` 请求级缓存 + `owner` 标识防串号；
- `ThreadLocal<Boolean> COMPUTING` 防递归；
- `isPatientDriven()` / `sqlVisiblePatientIds()` 区分「不受限（返回 null）」与「无可见患者（空集合）」；
- `CacheClearFilter` 在请求结束时清缓存。

本质矛盾：**拦截器在请求前介入，却依赖请求结果**，每增加一类用户口径就要再补一层补丁。

**改造后的方案（方案 B：只用 JWT 里的字段，不查库）**

可见口径只有一条：**患者已勾选科室包含医生所在科室**。因此条件可直接表达成静态子查询：

```sql
patient_id IN (SELECT d.patient_id FROM cd_patient_dept d WHERE d.dept_id = 当前医生科室)
```

渲染后在完整语句中的样子（实取自 `cd_health_score` 查询）：

```sql
... WHERE cd_health_score.patient_id IN (SELECT d.patient_id FROM cd_patient_dept AS d WHERE d.dept_id = 101)
```

判定规则（`PatientScopeInterceptor.scopeOf`，第 75 行）：

| 身份 | 行为 |
| --- | --- |
| 非患者相关表（系统表、字典表等） | 返回 `null`，不改写 |
| 未登录 / `mp` 小程序用户 / `user_type=2` 管理员 | 返回 `null`，不受限 |
| 医生且无科室 | 追加 `1 = 0`，看不到任何患者（避免退化成全量可见） |
| 医生且有科室 | 追加上述 `IN (子查询)` |

受益点：循环依赖从根源消失，`ThreadLocal` 缓存、防递归标记、清理过滤器全部删除。

**代码变更清单**

- `security/PatientDataScopeInterceptor.java` **删除**，新建 `security/PatientScopeInterceptor.java`（内容相同，仅改名，原因见 B 节）。
  - 第 35 行：`class PatientScopeInterceptor extends DataPermissionInterceptor`
  - 第 55 行：`public static PatientScopeInterceptor of(Supplier<LoginUser> loginUserSupplier)`
  - 第 75 行：`static Expression scopeOf(Table table, LoginUser user)`
  - 第 92 行：`deptPatientsSubSelect(Long deptId)` 负责构造子查询
- `config/MybatisPlusConfig.java` 重写：不再注入 `ObjectProvider<PatientDataScopeService>`，改为
  `interceptor.addInnerInterceptor(PatientScopeInterceptor.of(SecurityUtils::getLoginUserOrNull))`（第 29 行），顺序仍是「数据权限 → 分页」，保证 count 语句同样带范围条件。
- `modules/chronic/service/PatientDataScopeService.java`：删除仅供拦截器使用的 `restrictPatientIds()`、`isPatientDriven()`、`sqlVisiblePatientIds()`，只保留 `visiblePatientIds()`、`canAccess()`、`checkAccess()` 两个重载。
- `modules/chronic/service/impl/PatientDataScopeServiceImpl.java` 重写：删除 `ThreadLocal` 缓存、`COMPUTING`、`clearCache()`；`canAccess`（第 67 行）改为一次 `selectCount` + `inSql` 子查询判定。

- `cd_patient_dept` 表**没有逻辑删除列**，子查询无需额外条件。

### B. IDEA 显示「已从编译中排除」的排查与规避

**现象**：IDEA 中 `PatientDataScopeInterceptor.java` 一直显示为「已从编译中排除」。

**排查结论**

1. 记录确实存在于 `backend\.idea\compiler.xml` 的 `<excludeFromCompile>` 中，指向该文件的 URL。
2. 排除是**单文件级**的，并非 Maven 导入生成，也不属于目录/模块级排除；`.idea` 未被 git 跟踪，无法追溯改动者，判定为本地手工误操作。
3. 文件依赖（`mybatis-plus-jsqlparser`、jsqlparser）齐全，不存在「解析不了只能排除」的技术理由。
4. 删除 `<excludeFromCompile>` 块后，磁盘配置已干净，但**正在运行的 IDEA 仍显示排除**（配置缓存在内存中）。

**最终规避方式**：文件改名 + 新建同名类。

- 删除 `PatientDataScopeInterceptor.java`，新建 `PatientScopeInterceptor.java`，类名同步修改。
- 同步更新引用：`MybatisPlusConfig.java`、`PatientDataScopeServiceImpl.java` 的 Javadoc。
- 清理 `target/classes/com/chronic/security/` 下 3 个过期字节码（`PatientDataScopeInterceptor` 及两个内部类）。
- 若 IDEA 仍有残留，执行 `File → Reload from Disk`；再不行用 `File → Invalidate Caches / Restart`。

### C. 编译错误：jsqlparser 5.0 的 API 用法

改造过程中遇到并修复的两类问题，**jsqlparser 5.0 的构造函数语义与旧认知不同**，后续写同类代码请注意：

| 错误写法 | 报错 | 正确写法 |
| --- | --- | --- |
| `new Column("d", "patient_id")` | 无法解析构造函数 `Column(String, String)` | `new Column(new Table("d"), "patient_id")` |
| `new Table("cd_patient_dept", "d")` | 运行期 `Unknown database 'cd_patient_dept'` | `Table t = new Table("cd_patient_dept"); t.setAlias(new Alias("d"));` |

**原因**

- `Column` 只有 `Column(Table, String)`、`Column(String)`、`Column(List<String>)` 等重载，没有 `(String, String)`。
- `Table(String, String)` 的双参是**库名 + 表名**，不是表名 + 别名。误用会渲染成 `cd_patient_dept.d`，被 MySQL 当成「库 cd_patient_dept 下的表 d」。

已用项目自带的 `jsqlparser-5.0.jar` 单独验证渲染结果：

```
WITH_ALIAS   : h.patient_id IN (SELECT d.patient_id FROM cd_patient_dept AS d WHERE d.dept_id = 101)
WITHOUT_ALIAS: h.patient_id IN (SELECT d.patient_id FROM cd_patient_dept WHERE d.dept_id = 101)
```

第二行中 `d.dept_id` 引用未定义别名，同样会报错，故别名必须显式设置。

### D. 小程序端「患者看不到自己资料」修复

**现象**：小程序端登录患者账号后，档案页报「无权查看该患者数据」。

**日志**

```
DEBUG c.c.m.c.s.i.PatientDataScopeServiceImpl : 越权访问患者数据：userId=12345678901 patientId=11
WARN  c.c.c.exception.GlobalExceptionHandler   : 业务异常 [/mp/patient/detail] 无权查看该患者数据
```

**排查**

1. 数据库核对：`mp_user.user_id=112`（`12345678901`）对应 `cd_patient.patient_id=11` 且 `mp_user_id=112`，绑定关系正常 —— 归属校验本身没问题。
2. 调用链：`/mp/patient/detail` → `MpPatientServiceImpl.patientDetail` → `accessService.requirePatient(id)`（通过）→ `toVO(...)` → **`patientService.getPatientDetail(patientId)`**。
3. `CdPatientServiceImpl.getPatientDetail` 第一行是 `dataScopeService.checkAccess(patientId)`；而 `PatientDataScopeServiceImpl.canAccess` 对 `mp` 用户**直接返回 false**（本意是「小程序端不走医生数据范围」，却写成了拒绝）。

结果：小程序端先通过自己的归属校验，随后又被医生端的数据范围校验拦下。

**修复**：把「权限校验」与「数据组装」拆开。

- `CdPatientService.java:28` 新增 `PatientVO getPatientDetailUnscoped(Long patientId)`，注释明确「不做医生数据范围校验，调用方负责鉴权」。
- `CdPatientServiceImpl.java:132` 起：`getPatientDetail` = `checkAccess` + `buildPatientDetail`（医生端行为不变）；`getPatientDetailUnscoped` = `buildPatientDetail`；`private buildPatientDetail`（第 143 行）只做组装。
- `MpPatientServiceImpl.java:383` 改用 `getPatientDetailUnscoped`（其上一行 `accessService.requirePatient(id)` 已完成小程序归属校验）。

**核对结果**

- 小程序模块内已无任何 `checkAccess` / `dataScopeService` 引用。
- 小程序其余接口（diseases / indicators / dashboard / trend / 录入）均直接查 Mapper 或走 `requirePatient`，不存在同类问题。
- 医生端 `getPatientDetail` 行为未变。

## 三、遗留事项与注意事项

1. **未编译、未测试**：本次改动由使用者在 IDEA 中自行编译验证；已运行验证的是服务重启后的接口行为与上述日志。
2. **`cd_patient_dept` 无逻辑删除列**：若后续给该表加 `del_flag`，`PatientScopeInterceptor.deptPatientsSubSelect`（第 92 行）需同步加条件。
3. **JWT 科室快照**：拦截器用 JWT 中的 `deptId`，`checkAccess` 用数据库实时值。若要求「管理员改科室后列表立即生效」，可考虑在 `JwtAuthenticationFilter` 中按 userId 回查 `sys_user.dept_id`（会增加每请求一次查询，需权衡）。
4. **`ColumnUtils` 类风险提示（未修复，非本次范围）**：`PermissionService.hasRole` 仍使用 `inSql` 字符串拼接 `userId`（入参为 `Long`，风险低）。
5. **`application.yml` 中的明文敏感信息**：`chronic.jwt.secret` 与 DeepSeek `api-key` 仍以明文提交，建议后续改为环境变量。
6. **`/mp/**` 仅要求登录**：`SecurityConfig` 中 `AntPathRequestMatcher("/mp/**")).authenticated()` 未限制 `userType=mp`，后台医生账号理论上也可调用小程序接口（接口内部另有归属校验，但无 `userType` 断言）。若需严格隔离，可改为 `hasRole('MP')`。
